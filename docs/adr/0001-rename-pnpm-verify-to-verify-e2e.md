# 1. 将 pnpm verify 重命名为 pnpm verify:e2e 以消除与 /verify 的命名冲突

- 状态：提议（机器推断）
- 日期：2026-08-21

## 上下文

项目中存在两个名称高度相似的命令：`/verify`（斜杠命令，用于修 bug 后的唯一复审，只审 git diff）和 `pnpm verify`（终端命令，作为 release 门禁，重跑 4 评审员并调用真实后台）。两者规则散落在 AGENTS.md 的七处（line 58/61/76/78/134/137/174），从未并排对照，导致 AI 在读取规则时发生混淆，将「门禁不进编辑循环」的规则错误套用到 `/verify` 上，造成该跑的复审未跑。根因是命名撞车，仅靠文档补丁无法彻底防止未来再次混淆。

## 决策

### 本质
命名冲突（`/verify` 与 `pnpm verify` 名字高度相似）导致 AI 串读规则；可逆（改名可回退）、无损（重命名 + 改引用）。

### 最佳实践
命名撞车的根治是「物理消除歧义」（改名），而非「文档补丁」（治标不治本）。

### 方案
将 `package.json` 中的 `verify` script 重命名为 `verify:e2e`，并同步更新所有引用：AGENTS.md 中 4 处（line 58/76/78/137）、README.md 中 1 处（line 229）、docs/verification.md 中 4 处历史台账锚点。改名后，`/verify` 与 `pnpm verify:e2e` 在名称上不再相似，从物理上杜绝串读。

## 后果

正面：彻底消除命名歧义，AI 和人类都不会再因名字相似而混淆两个不同性质的检查；规则收敛后，`/verify` 作为「修 bug 后唯一复审」的定位更清晰，`pnpm verify:e2e` 作为「release 门禁」的定位也更明确。负面：改名是有损变更，需要同步修改项目内所有引用（已通过 grep 核清共 6 处核心引用 + 4 处台账，无外部依赖）；历史文档中的旧命令名需要一并更新，否则旧记录可能误导读者。

## 被拒备选

仅靠文档补丁（如加对照表、收窄 ⏸️ 枚举）而不改名：只能防住本次的具体错误，无法防止未来出现其他名称相似的新命令时再次混淆，属于治标不治本；保留原名但增加更醒目的警告：无法从根本上消除歧义，且警告容易被忽略，效果不可靠。
