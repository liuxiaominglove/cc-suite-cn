# 2. 在 AGENTS.md 中新增「复审 vs 门禁」对照表并收窄「尚未复审」状态为三种枚举

- 状态：提议（机器推断）
- 日期：2026-08-21

## 上下文

AGENTS.md 中关于 `/verify`（修 bug 后唯一复审）和 `pnpm verify`（release 门禁）的规则散落在七处，从未并排对照，导致 AI 在读取时发生「串读」——将「门禁不进编辑循环」的规则错误套用到 `/verify` 上，造成该跑的复审未跑。同时，AGENTS.md 第 175 行对「⏸️ 尚未复审」状态的描述过于模糊（「卡在哪 + 需要用户做什么」），给了 AI 使用「门禁借口」来豁免复审的空间。

## 决策

### 本质
规则散落 + 模糊措辞给「门禁借口」留了空间；可逆（改文档）、无损。

### 最佳实践
散落的规则收敛成单一对照表；模糊状态收窄成可枚举的客观理由（防借口）。

### 方案
在 AGENTS.md 的 Verification Discipline 段（第 134 行旁）新增一张对照表，将三个容易混淆的命令并排列出：`/verify`（修 bug 后唯一复审，每次改完代码必跑，opencode 自动发起，1 次）、`pnpm verify:e2e`（release 门禁，仅 release/推前跑，用户手动发起，1 次）、`pnpm test:unit`（内循环单测，改代码随手跑，任意发起，不限次数）。同时，将第 175 行的「⏸️ 尚未复审」状态收窄为只允许三种客观理由：`git diff` 空（无改动可审）、真机/UI 验证需用户授权/在场、评审员空输出且重试耗尽。并明确加注：「门禁不进编辑循环」不是标 ⏸️ 的合法理由——那条管 `pnpm verify:e2e`，与 `/verify` 无关。

## 后果

正面：规则从七处散落收敛为一目了然的对照表，AI 和人类都能快速区分三个命令的性质、时机、发起者和次数；「⏸️ 尚未复审」的三种枚举锁死了模糊借口，下次标 ⏸️ 必须有客观理由，否则即违规。负面：需要修改 AGENTS.md 的既有内容，可能影响其他依赖该文件规则的流程；对照表需要保持更新，若未来新增类似命令需同步补充。

## 被拒备选

仅靠口头提醒或临时纠正：无法防止未来再次发生，且不改变规则散落的根本问题；不修改 AGENTS.md 而只在 SKILL.md 中提醒：SKILL.md 只在特定流程中加载，无法覆盖所有读取 AGENTS.md 的场景，覆盖面不足。
