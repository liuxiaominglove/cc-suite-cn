# 19. /verify 区分「本次修复 diff」与「预先存在的未提交改动」

- 状态：提议
- 日期：2026-09-01

## 上下文

对 parallel 项目跑 `/fix` 时，被审项目工作区**本来就有一批未提交的功能改动**（约 350 行），opencode 的修 bug 叠加其上。复盘暴露两条问题：

1. `/verify` 复审用 `git diff HEAD` 当「本次改动」，但当被审项目有未提交改动时，diff 混入「预先存在的功能 + 本次修复」，复审施工队把一半火力花在预先存在的旧代码上，稀释了「只审我的改动」的意图。
2. 审计落账的 `auditCommit` 记的是 `git rev-parse HEAD`，但被审文件实际是「HEAD + 未提交改动」。`auditCommit` 语义上声称「审计时在哪个 commit」，却和真实被审内容脱节（内容防篡改靠的是 `codeHash`，二者维度不同）。

## 决策

### 本质

- 改进 1 本质是「缺基线，增量边界模糊」：要界定「本次修复改了什么」，必须先有「修前起点快照」。`git diff HEAD` 拿的是「HEAD → 现在」，但 HEAD 不是「本次修复的起点」（工作区里本来就有未提交改动）。属**数据/流程**类，可逆、无损。
- 改进 2 本质是「标识符错配」：把 git commit hash（版本历史位置标识）当「内容快照标识」用。commit 描述「历史位置」，`codeHash` 才描述「内容」；工作区有未提交改动时二者脱节。属**数据建模**类，可逆。

### 最佳实践

git 界定增量的标准做法是「基线快照」：`git diff <base>` 必须先明确 base；没有明确的起点，任何「本次改动」都是伪命题。标识符应单一职责——版本位置用 commit、内容用 content hash，不能互相顶替。项目先例已有正确的内容标识（`codeHash` + `isVerdictStale`），缺的只是「修复起点」这一维。

### 方案

- 改进 1：修 bug 前对被改文件做「修前快照」，`/verify` 时 diff「修前 → 现在」而非「HEAD → 现在」。落地候选：`markFixed` 记录 `preFixHash`（修前内容 hash），或引入显式基线文件；当被审项目无未提交改动时退化为 `git diff HEAD`（现状）。
- 改进 2：在 `AGENTS.md`/`verdict-log.mjs` 明确 `auditCommit` 语义 =「审计时的 git HEAD（仅作版本锚点，供按轮次隔离）」，内容是否失效一律以 `codeHash` 判定，`auditCommit` 不承担内容校验职责。

## 后果

正面：`/verify` 对被审项目带未提交改动时审对范围，复审信号更干净；`auditCommit`/`codeHash` 职责清晰、防误判。负面：改进 1 需引入基线快照机制，改动面大、有回归风险，属「增量审计」通用难题，需先设计再实现。

## 被拒备选

- 复用 `git stash` 临时存未提交改动、审完再恢复：被拒——有副作用、易出错，且会扰动用户的工作区状态，违背「只读评审」原则。
- 改进 2 直接弃用 `auditCommit` 改存 `codeHash`：被拒——按轮次隔离仍需「版本位置」锚点，二者维度不同、都该保留。
